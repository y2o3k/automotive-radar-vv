# 첫 CI 실습: 시험 실패를 정확히 전달하기

## 학습 목표

기존 FCW 요구사항과 6개 Test Case를 사용해 다음 흐름을 이해한다.

`코드 변경 → 자동 시험 → 종료 코드 판정 → 결과 CSV·로그 보관`

CI는 시험의 타당성을 대신 판단하지 않는다. 요구사항에 맞는 예상 결과와
그 결과를 비교하는 시험이 먼저 필요하다. 현재 TTC 기준은 학습용 가정이다.

## 발견한 문제

기존 실행기는 `FAIL`을 출력해도 정상 종료 코드 `0`을 반환했다.
따라서 GitHub Actions에 그대로 연결하면 결함이 있어도 성공으로 표시될 수 있었다.
수정한 실행기는 시험 실패 시 `1`, 빈 시험 목록·입력 오류 시 `2`를 반환한다.
결과 파일은 정상적으로 실행을 마친 경우에만 작성하며, FAIL 행도 보관한다.
입력 오류로 완료하지 못한 실행에는 이전 PASS 결과를 남겨두지 않는다.

## 경계값 결함으로 확인하기

현재 구현은 `TTC <= 2.0`이면 ON이다. 이를 `TTC < 2.0`으로 바꾸면:

| 항목 | 예상 |
|---|---|
| 위반 요구사항 | REQ-FCW-001 |
| 검출 시험 | TC-FCW-002 |
| 입력 | 거리 20m, 상대속도 -10m/s |
| 계산 TTC | 2.0s |
| 요구 결과 / 결함 구현 결과 | ON / OFF |
| CSV | TC-FCW-002가 FAIL |
| 실행기 종료 코드 | 1 |

`tests/test_runner.py`는 임시 복사본에만 이 결함을 주입하고 위 결과를 확인한다.
따라서 **결함을 정확히 잡아낸 검증 자체는 PASS**가 된다. 실제 프로젝트 소스는 수정하지 않는다.
이 자동 확인은 Actions가 임의의 실패를 무시하도록 설정된 것이 아니다.

직접 빨간 CI → 수정 후 초록 CI를 경험하려면 별도 학습 브랜치에서 해당 비교 연산자만
바꾸고 push한다. Actions의 `Run FCW regression` 단계가 실패하고 CSV에 TC-FCW-002가
FAIL인지 확인한다. 그런 다음 `<=`로 되돌려 push하고 전체 PASS를 확인한다.
결함을 넣은 상태는 main에 반영하지 않는다.

## 결과 읽는 순서

1. GitHub **Actions → FCW validation**에서 실행을 선택한다.
2. 시험한 브랜치와 커밋을 확인한다.
3. `Run FCW regression`의 6개 TC 결과를 읽는다.
4. 실행기 검증에서 정상·경계값 결함·빈 CSV·잘못된 숫자 입력의 처리를 확인한다.
5. **Artifacts → fcw-test-evidence**에서 결과 CSV와 검증 로그를 내려받는다.
6. 실패한 TC의 requirement_id로 요구사항 문서를 찾아 예상 결과의 근거를 설명한다.

## 스스로 설명할 것

- CSV에 FAIL이 있어도 종료 코드가 0이면 CI는 왜 성공으로 보일까?
- TTC 2.0초 시험은 `<`와 `<=`의 차이를 어떻게 검출할까?
- 시험 0개가 PASS로 처리되면 어떤 문제가 생길까?
- 결함 주입 검사가 PASS라는 것과 제품 시험이 PASS라는 것은 어떻게 다를까?

## 다음 단계와 범위

다음 기능은 메시지 유효성·수신 타임아웃이다. 먼저 요구사항과 시간 경계 시험을 정의하고,
이후 RTOS 작업·큐·타이머로 구현해 같은 CI 흐름에 연결한다.
현재 단계만으로 RTOS 실행시간, 실제 CAN 통신, ECU/HIL, 기능안전 적합성을 검증했다고 주장하지 않는다.
CI 성공은 main 병합 제한을 자동 설정하지 않는다. 필수 검사 정책은 별도의 저장소 설정이다.
